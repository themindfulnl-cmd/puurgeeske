# PuurGeeske

The website for PuurGeeske — yoga, pilates, breathwork, massage and coaching
with Geeske in Hoofddorp.

Live at **[puurgeeske.nl](https://www.puurgeeske.nl)**.

Next.js 16 (App Router) · React 19 · Tailwind 4 · deployed on Vercel from
`main`. Every push to `main` deploys to production automatically.

```bash
npm install
npm run dev      # http://localhost:3000
npm run build    # production build
npm run lint
```

---

## How it's put together

```
app/                  pages (App Router)
  page.tsx            the homepage
  blog/ over/ contact/
  admin/              the content dashboard (password protected)
  api/admin/          login + logout
components/
  sections/           the homepage sections, in page order
  layout/             navbar, footer
  ui/                 Button, Card, Picture, FilmPlayer, ScrollReveal
lib/
  content.ts          reads the JSON content files
  data/*.json         the actual content — services, events, reviews, blog
  auth.ts             admin sessions
proxy.ts              guards /admin before any page renders
public/
  opt/                pre-made image sizes (see below)
  videos/             Geeske's two films
scripts/
  gen-images.sh       regenerates public/opt
  gen-videos.sh       regenerates the 720p mobile cuts
```

The homepage is static with hourly regeneration. The only reason it
regenerates at all is so past workshops drop off the agenda by themselves.

## The two films

Both live in `public/videos/` and are committed to this repo. They are served
as static files straight from Vercel's CDN — there is no Bunny, YouTube or
Vimeo involved.

| File | Length | Size | Where it appears |
|---|---|---|---|
| `intro.mp4` | 1:30 | 13 MB | the hero, top of the homepage |
| `intro-720.mp4` | 1:30 | 8.8 MB | same film, sent to phones |
| `nazomer.mp4` | 3:50 | 36 MB | "De Nazomer", below the fold |
| `nazomer-720.mp4` | 3:50 | 24 MB | same film, sent to phones |

That is ~83 MB in the repo. It works, but a CDN is the better long-term home
once there are more films.

**How playback works.** The `<video>` element isn't created until someone taps
play — before that it's just a poster image, so a visitor who never watches the
films downloads none of it. On tap, `FilmPlayer` picks the 720p cut for phones,
small screens, or anyone on a metered or 2G/3G connection, and the 1080p
master for everyone else. Both are encoded faststart, so playback begins while
the rest is still arriving.

Nothing autoplays. Geeske speaks in both films.

To re-make the mobile cuts after replacing a master: `./scripts/gen-videos.sh`

## Images

`public/images/` holds the originals. `public/opt/` holds pre-made AVIF, WebP
and JPEG versions at several widths, generated by `./scripts/gen-images.sh` and
committed.

They're built ahead of time rather than resized on the fly, so a cold visit
never waits on an image optimizer. The `Picture` component picks the right one
per screen — a phone gets roughly a tenth of what a desktop does.

**After adding or replacing an image**: add it to `scripts/gen-images.sh`, run
the script, commit what lands in `public/opt/`.

## Editing content

Everything on the site reads from `lib/data/*.json`:

| File | What it holds |
|---|---|
| `services.json` | the six offerings |
| `events.json` | the workshop agenda |
| `reviews.json` | testimonials |
| `blog.json` | blog posts |
| `config.json` | email, address, social links, booking URL |

Edit the JSON, commit, push — the site rebuilds.

**The `/admin` dashboard can only read, not save.** Vercel's filesystem is
read-only, so writes fail with a clear message rather than silently doing
nothing. Making the dashboard actually save needs a real store (Vercel Blob or
Supabase); until then, the JSON files are the source of truth.

> **Note:** every event in `events.json` is dated 2025, so the agenda shows its
> empty state. Add current dates to bring the section back.

## The admin area

`/admin`, behind a password. `proxy.ts` checks the session at the edge before
any admin page renders.

Two environment variables are required in Vercel, and admin is disabled
without them rather than falling back to anything:

| Variable | Purpose |
|---|---|
| `ADMIN_PASSWORD` | the login password |
| `ADMIN_SESSION_SECRET` | signs session cookies (needs 32+ characters) |

Sessions are signed and expire after 12 hours. Login is limited to 8 attempts
per 15 minutes.

For local development:

```bash
ADMIN_SESSION_SECRET="any-long-random-string-at-least-32-chars" \
ADMIN_PASSWORD="something" \
npm run dev
```

## Keeping it fast

The site was rebuilt for mobile on 2026-08-26. First paint went from 5.2
seconds to 268ms. Almost all of that was one thing: two enormous CSS blur
effects in the hero.

A few rules worth keeping:

- **No `filter: blur()` or `backdrop-filter`.** A large blur makes the browser
  rasterize a huge texture and run a gaussian over it. Desktop GPUs hide the
  cost; phones can't. This is what made the site slow.
- **Animate only `opacity` and `transform`.** Both run on the GPU and cost
  nothing to paint. Anything else risks layout and repaint work.
- **Keep hover effects inside `@media (hover: hover)`** so touch devices never
  pay for them.
- **Don't add framer-motion back.** It cost ~110KB to fade sections in; CSS and
  one `IntersectionObserver` do the same in about 1KB.
- **Sections should stay server components.** Only the navbar and the film
  player need to run in the browser.
- **Content must never depend on JS to be visible.** Scroll reveals are opt-in:
  elements are visible by default and only animate once an inline script marks
  the page as JS-capable. If the script fails, the page still reads.

Roughly where things stand on a phone, first visit: ~14KB of HTML, ~9KB of CSS,
~36KB of images above the fold, fonts and JS after that. Everything in
`/opt`, `/images` and `/videos` is cached for a year, so repeat visits are
nearly free.
